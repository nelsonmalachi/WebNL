New-AzureNaming.ps1 
<#
.SYNOPSIS
    Erstellt standardkonforme Azure-Ressourcennamen.
.NOTES
    Author : NLA
.HISTORY
    NLA - 2024-04-24 - 1.0.0 - Initiale Version
#>

function New-StorageAccountName {
    param (
        [string]$customerCode,
        [string]$location = 'chn1',
        [int]$instance    = 1
    )

    # Maximal 24 Zeichen, nur Kleinbuchstaben
    $pattern = '{0}boot{1}sa{2:d2}'
    $name    = $pattern -f $customerCode, $location, $instance

    return $name.ToLower()
}

01Profil

Standardisierung ist kein Selbstzweck

Ich bin Cloud Engineer bei Axians Somnitec AG und beschäftige mich täglich damit, wie Enterprise-Umgebungen auf Azure sauber aufgesetzt, dokumentiert und wiederholbar betrieben werden.

Der Reiz liegt selten im spektakulären Einzelfall, sondern im Muster dahinter: eine Namenskonvention, die für 5 und für 500 Ressourcen funktioniert. Ein Backup-Konzept, das nicht von der Tagesform abhängt. Ein Skript, das in zwei Jahren noch lesbar ist, weil der Header erklärt, warum es existiert.

Was ich abliefere, soll übergebbar sein. Wenn jemand anderes meine Arbeit weiterführen kann, ohne mich zu fragen, dann ist sie fertig.

02Expertise

Vier Dinge, die ich gut kann

Infrastructure as Code

Terraform-Module für wiederkehrende Azure-Bausteine: Landing Zones, Netzwerke, Storage, Governance. Sauber versioniert, mit State-Handling, das auch im Team funktioniert.

PowerShell Automation

Skripte nach festen Guidelines: strukturierter Header, Regionen für Module, Variablen und Methoden, Verb-Noun-Funktionen und semantische Versionierung. Nachvollziehbar statt clever.

Konventionen & Dokumentation
